# ADR-0063: SSTV receive and transmit

- **Status:** Proposed
- **Date:** 2026-11-07

## Context

The [roadmap](../04-roadmap.md) adds SSTV in two milestones, receive and transmit. The first one
starts with two decisions: which modes the app supports, and whether an existing library is reused or
the decoder is written from scratch, including its licence. This ADR records the research for both
milestones, before any code is written.

Facts of the project that bound the choice:

- **Audio:** the radio sends 16 kHz mono as IMA ADPCM ([ADR-0020](0020-rx-audio-pipeline.md)). SSTV
  lies between 1100 and 2300 Hz, well below the Nyquist limit. Whether the 4-bit ADPCM adds visible
  noise to an image is not known yet.
- **Transmit time:** the firmware ends a transmission after 200 s
  ([ADR-0021](0021-tx-audio-and-ptt.md)). Robot 36 (about 36 s), Martin M1 (about 114 s), Scottie S1
  (about 110 s), PD120 (about 126 s) and PD180 (about 187 s) fit. PD240, PD290 and Scottie DX do not.
- **Licence:** the app is under GPL 3.0 and goes to the App Store. Third-party GPL code is the known
  problem case there, so only permissive licences are considered for code that enters the app.
- **No oracle from Android:** the Android app has no SSTV, so the golden test vectors of
  [ADR-0004](0004-android-code-reuse.md) cannot come from it. An oracle has to come from elsewhere.

Licences were read through the GitHub API, and the size of the code was measured on clones.

## Considered options

| Candidate | Language | Licence | Covers | Assessment |
|---|---|---|---|---|
| [Robot36](https://github.com/xdsopl/robot36) | Java | 0BSD | Decoder: Robot 36/72, Martin 1/2, Scottie 1/2/DX, PD 50–290, Wraase SC2-180, HF fax; mode detection | Maintained for years and on [F-Droid](https://f-droid.org/en/packages/xdsopl.robot36/). The decoding core is about 2,300 lines and depends only on `android.graphics.Bitmap`. |
| [SSTV-MEL](https://swiftpackageindex.com/kevinnz/SSTV-MEL) | Swift | MIT | Decoder: PD120, PD180, Robot 36 | Could be used directly, but has too few modes and a single developer. Useful for reading. |
| [slowrx](https://github.com/windytan/slowrx) | C | ISC | Decoder | Marked as unmaintained by its repository. A young [Rust port](https://docs.rs/crate/slowrx/latest) exists (MIT). |
| [libsstv](https://ports.macports.org/port/libsstv/) | C | MIT | Encoder only, over 30 modes (Martin, Scottie, PD, Robot) | A decoder is planned but not started. Suits an oracle for the encoder. |
| [PySSTV](https://pypi.org/project/PySSTV/) | Python | MIT | Encoder | Maintained; also suits an oracle for the encoder. |
| QSSTV, MMSSTV, [colaclanth/sstv](https://github.com/colaclanth/sstv) | C++, Python | GPL 3.0 | Decoder and encoder | The licence rules them out for the App Store. |

For each direction, three ways were looked at:

1. **Use a library as it is.** Only SSTV-MEL is Swift, and it lacks Martin and Scottie, the most used
   modes. A C library inside the app adds a build of its own, and none of the permissive C ones decodes
   and is maintained.
2. **Port a library to Swift,** as [ADR-0023](0023-aprs-receive-path.md) did with java-aprs. The
   original then runs unmodified as a test oracle.
3. **Write it from scratch.**

**The encoder is simple.** SSTV is frequency modulated: each pixel is a tone between 1500 Hz (black)
and 2300 Hz (white), with sync pulses at 1200 Hz and a VIS code at the start that names the mode. It
needs a phase-continuous oscillator and a timing table per mode, a few hundred lines of Swift. The
callsign is drawn into the image beforehand with Core Graphics.

**The decoder is the hard part.** The idea is simple: demodulate the frequency, find the sync pulses,
place the lines and convert the colours. The quality on real reception depends on details: sync in
noise, correcting slanted images caused by clock drift between sender and receiver, and finding the
mode without a VIS code. Robot36 has refined exactly that over years, and writing it from scratch
would redo that work.

## Decision

- **Receive: port the Robot36 decoder to Swift.** The unmodified Java code runs in
  `tools/test-vectors/` as the test oracle, with a small stand-in for `android.graphics.Bitmap`, the
  same way as the Android code today. The JDK it needs is there already. 0BSD asks for no notice,
  but About and the FAQ name Robot36 anyway.
- **Transmit: write the encoder in Swift.** It is tested three ways, so that encoder and decoder
  do not only confirm each other:
  - a round trip from the encoder through the Swift decoder, as the roadmap asks;
  - a comparison with libsstv or PySSTV as an independent oracle, run in `tools/`, outside the app;
  - Robot36 in Java decoding the signal of the new encoder.
- **Modes to start with:** Robot 36, Martin M1, Scottie S1, PD120 and PD180. They are the common ones,
  the ISS uses PD120 and PD180, and all fit into the 200 s of the firmware. The decoder may receive
  more of the modes Robot36 knows, as receiving has no time limit.

## Consequences

- An early test with a recording from a real radio has to show whether SSTV through the ADPCM path is
  clean enough, before the decoder is tuned on generated signals only.
- The port follows Robot36 upstream by hand. Its small size and its stable core keep that manageable.
- The oracles for the encoder add Python or a C build to the tools, not to the app.
- Whether HF fax, which Robot36 also brings, is worth offering is left open, as it is of little use on
  VHF FM.
- Modes longer than 200 s wait until the firmware allows longer transmissions, as a separate step.
- The two milestones may refine the details here; a change of the decision itself needs a new ADR.
