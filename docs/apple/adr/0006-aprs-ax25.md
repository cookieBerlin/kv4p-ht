# ADR-0006: APRS and AX.25 implementation

- **Status:** Accepted
- **Date:** 2026-10-31

## Context

Current firmware modulates and demodulates AFSK itself
(`FEATURE_HAS_ESP32_AFSK`); the host only exchanges AX.25 frames in KISS DATA
frames. Android builds and parses AX.25 with its own `javAX25` package and APRS
with the JVM library `io.github.dkaukov:java-aprs` (parser, beaconing, APRS-IS
client). None of this runs on Apple platforms.

## Considered options

1. **Own Swift implementation** of AX.25 (address/control/PID framing) and the
   APRS subset used by the Android app (position, messages, objects, status,
   station capabilities), plus an APRS-IS TCP client.
2. **Existing C library** (e.g. from Dire Wolf / aprslib) wrapped in Swift — larger
   surface, licensing and maintenance overhead for features we do not use.
3. **Host-side AFSK modem** — unnecessary for current firmware.

## Decision

Option 1, implemented test-first against golden vectors generated from
`javAX25` and `java-aprs` ([ADR-0004](0004-android-code-reuse.md)). Scope grows
with the feature inventory in [01-feasibility.md](../01-feasibility.md).

## Consequences

- Full control and 100 % coverage of the APRS code.
- Firmware without `HAS_ESP32_AFSK` is not supported for APRS on Apple.
- Parser completeness is a risk; unsupported packet types are shown raw.
